# 行为闭环与服务可靠性规范

## 范围

本规范定义行为数据如何形成可核对的反馈闭环，以及社区核心、发现和 Assistant 能力在正常与故障
状态下必须提供的可观测性和降级行为。不规定消息中间件、分析数据库、指标系统或部署拓扑。

## 术语

- **客户端事件**：客户端针对曝光、点击、停留或其他用户动作提交的行为记录。
- **已接受事件**：通过校验并进入系统承诺的可靠处理边界、可被后续去重和处理的事件。
- **业务效果**：一次事件对特征、统计、推荐或其他下游状态产生的可观察影响。
- **降级**：依赖故障时保留边界清晰的有限能力，而不是伪造正常结果。

## 行为事件契约

- `REL-001`：每个客户端事件必须具有稳定且可去重的事件标识、动作、目标、发生时间和场景。
- `REL-002`：事件必须关联已认证用户或匿名身份；适用时应携带会话和发现请求标识，且不得归属到
  其他身份或请求。
- `REL-003`：推荐曝光应携带内容标识、展示位置、召回来源、规则或模型版本和实验标识中适用的字段；
  停留类事件应能表达有效时长。
- `REL-004`：批量提交必须逐项返回接受或拒绝结果；部分事件无效时不得把整个批次伪装成全部成功。
- `REL-005`：只有进入可靠处理边界的事件可以报告为已接受；无法确认接收时必须报告可识别的失败。
- `REL-006`：相同事件标识重复提交时，下游最多产生一次业务效果；重试不得重复累计特征或统计。
- `REL-007`：只被召回但未实际曝光的内容不得作为用户负反馈；推断负反馈必须能追溯到真实曝光。
- `REL-008`：过期、超前、缺少身份或结构无效的事件必须被拒绝，并给出可归类原因。

## 反馈闭环

- `REL-010`：已接受事件必须能够按请求、用户或匿名身份、内容、位置、来源、版本和实验维度关联，
  以区分候选、曝光和后续动作。
- `REL-011`：行为影响推荐前必须经过合法性和去重处理；拒绝事件不得进入训练或在线特征。
- `REL-012`：系统必须能够区分规则结果、模型结果和降级结果，避免把不同策略的数据混为同一效果。
- `REL-013`：反馈处理允许异步完成，但必须能观察处理延迟、失败和积压；不得用接口接收成功证明闭环已完成。
- `REL-014`：历史事件重放或消费者重启不得改变去重语义，也不得静默产生额外业务效果。

## 可观测性

- `REL-020`：对外服务必须提供可判断存活与就绪状态的健康信号；依赖未就绪时不得报告完全健康。
- `REL-021`：社区核心、发现、Assistant 和行为链路必须能够观察请求量、成功率、错误类别和延迟。
- `REL-022`：异步链路必须能够观察事件接收、拒绝、重复、处理失败、重试、积压和端到端延迟。
- `REL-023`：推荐与 Assistant 必须能够区分正常、部分降级、规则降级、证据不足和完全不可用。
- `REL-024`：同一请求跨能力调用时必须保留可关联的请求或追踪标识；日志不得记录 secret 或不必要的私密内容。

## 故障与降级

- `REL-030`：任何能力无法确认写入成功时都不得返回错误成功；重试边界必须对调用方可判断。
- `REL-031`：推荐依赖失败时只可返回符合 `SPEC-content-discovery` 的降级内容，不能验证可见性时必须失败。
- `REL-032`：Assistant 依赖失败时只可返回符合 `SPEC-grounded-assistant` 的拒答或降级结果，不得无证据生成。
- `REL-033`：行为处理失败不得阻止无关的社区读取，但必须保留可重试或可恢复状态并产生告警信号。
- `REL-034`：单个下游或消费者故障不得扩散为全平台错误成功、跨用户数据泄漏或不可恢复的数据覆盖。
- `REL-035`：服务恢复后必须能够继续处理合法新请求，并对故障期间保留的可重试工作进行有界恢复。

## 兼容边界

- `REL-040`：`/api/v2/behavior/events` 及其行为事件必须带可识别的模式版本；新增字段优先采用兼容扩展，
  破坏性变化必须使用新版本和迁移期。
- `REL-041`：同一事件版本中，事件标识、身份、动作、目标、请求和推荐归因字段的含义不得静默改变。
- `REL-042`：观测系统、消息系统和存储可以替换，但接受语义、去重语义、追踪关联和降级边界必须保持。

## 验收标准

- `REL-A01`：提交包含合法、重复、过期、超前、缺少身份和结构无效事件的批次，验证逐项结果和去重效果。
- `REL-A02`：完成一次“推荐结果 → 客户端曝光 → 后续动作 → 反馈处理”的链路，验证所有归因字段可以关联。
- `REL-A03`：重放相同事件并重启处理组件，验证最终业务效果不重复且处理状态可观察。
- `REL-A04`：分别注入发现、Assistant、事件接收和异步处理依赖故障，验证规定的失败或降级行为。
- `REL-A05`：验证健康、请求、错误、延迟、降级、积压和事件延迟信号存在，并能通过同一请求标识关联故障。
- `REL-A06`：验证日志和错误响应不包含 secret、内部堆栈或不必要的私密内容。

## 待人类确认

以下问题不构成本草案要求：

- 各核心链路的可用性、延迟、错误率、数据丢失和恢复时间量化目标。
- 匿名标识、行为采集同意、数据最小化、保留期限、删除和导出要求。
- 哪些动作可以作为正负反馈，以及曝光可见比例和最短停留时间。
- 各依赖故障时必须降级还是允许直接失败的完整决策矩阵。
